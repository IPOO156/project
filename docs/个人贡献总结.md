## 四、核心贡献深度解析（考察重点）

### 4.1 【稳定性】401 令牌刷新治理 —— 最能体现深度的一项

**代码位置**：`src/shared/api/request.ts`

#### 背景（Bug 现象）

用户点「退出登录」后页面以约 150ms 一次的频率无限 reload；登录页输错密码时会把已登录用户误登出。根因是**把所有 401 都当成"令牌过期"处理**，而实际上 401 有四种语义。

#### 方案：四层防护

**① 刷新单飞（Singleton）—— 解决并发重复刷新**

```typescript
let refreshPromise: Promise<string | null> | null = null

function tryRefreshToken(): Promise<string | null> {
  const refreshToken = getRefreshToken()
  if (!refreshToken) return Promise.resolve(null)
  if (!refreshPromise) {
    // 第一个 401 发起刷新
    refreshPromise = request
      .post('/auth/refresh', { refreshToken })
      .then(/* 回写新令牌 */)
      .finally(() => {
        refreshPromise = null
      })
  }
  return refreshPromise // 并发的其他 401 复用同一个 Promise
}
```

> **为什么单飞**：页面加载时十几个请求同时 401，若各自刷新，第一个成功后 `refreshToken` 已轮换（后端一次性），后续刷新全部失败 → 全部被登出。单飞保证同一时刻只有一个刷新请求。

**② 重试上限 —— 解决无限循环**

```typescript
if (((error.config as any).refreshCount || 0) < 3) {
  return tryRefreshToken().then((token) => {
    ;(error.config as any).refreshCount = ((error.config as any).refreshCount || 0) + 1
    error.config.headers = { ...error.config.headers, Authorization: `Bearer ${token}` }
    return request(error.config) // 带新令牌原样重试
  })
}
```

> **为什么计数器挂在 `error.config` 而不是全局变量**：每个请求的 401 重试次数应当独立统计；axios 的 config 对象在重试链中原样传递，天然是"随请求走"的载体。全局变量会导致 A 请求的重试耗尽配额影响 B 请求。

**③ 业务 401 分流 —— 解决误登出**

```typescript
function isBusiness401(url = '') {
  return (
    url.includes('/auth/login') || url.includes('/auth/password') || url.includes('/auth/logout')
  )
}
```

> **语义区分**：登录/修改密码返回 401 是"凭据有误"，退出登录返回 401 是"会话已清理"——它们都不是"令牌过期"。若走刷新链：改密码输错旧密码会把用户登出；登出请求 401 会反向触发刷新 → 死循环。

**④ 匿名 401 下抛 —— 解决整页 reload 死循环**

```typescript
const hadToken = Boolean(error.config?.headers?.Authorization)
if (!hadToken) return Promise.reject(error) // 未带 token 的 401 直接下抛
```

配合 `forceLogout()` 里的路径守卫（已在 `/login` 时不再赋值 `location.href`，避免同 URL 赋值触发 reload）。

> **场景还原**：登录页会请求设计为公开但后端白名单未放行的接口（如 `/public/statistics`），匿名 401 → forceLogout → 整页 reload → 又请求 → 又 401……约 150ms 一次。修复：匿名 401 不走刷新/登出，下抛给调用方 catch 静默处理。

**⑤ 附带细节：令牌回写保源**

刷新成功回写新令牌时用 `writeTokenPreservingSource()`——沿用旧 token 的存储位置（localStorage vs sessionStorage），避免勾了「记住我」的用户刷新一次令牌就降级成会话级登录。

#### 结果

提交「2026/09/07-前端-退出登录 401 死循环修复与接口去重治理」（15 文件 +440/-110），登录态相关零回归。

### 4.2 【性能】Store 双层请求去重 —— 全局推广的模式

**代码位置**：`src/app/stores/submission.ts`（最典型，带 5 步注释）、`archive.ts` 等 9 个 Store

#### 背景

多个页面/组件共享同一 Store，onMounted 各自 fetch：并发时同一接口连发多次；切换页面又对 60 秒内已拉过的数据重复请求。

#### 方案：两把锁解决两类问题

```typescript
let pendingFetch: Promise<void> | null = null // 锁1：防并发重入
let lastFetchedAt = 0 // 锁2：防跨页冗余
const CACHE_TTL_MS = 60_000

async function fetchRecords(filters?: SubmissionFilters, force = false) {
  if (pendingFetch) return pendingFetch // ① 在飞的直接复用

  const isFiltered = !!filters
  if (
    !force &&
    !isFiltered &&
    Date.now() - lastFetchedAt < CACHE_TTL_MS &&
    records.value.length > 0
  ) {
    // ② TTL 内用缓存
    filteredRecords.value = records.value
    return
  }

  pendingFetch = (async () => {
    // ③ IIFE 整段包进 Promise
    const raw = isFiltered ? await getSubmissionRecords(filters) : await getSubmissionRecords() // ④ 带条件只发一次
    if (!isFiltered) {
      records.value = raw // ⑤ 只有全量才写缓存+时间戳
      lastFetchedAt = Date.now()
    }
  })()
  try {
    await pendingFetch
  } finally {
    pendingFetch = null
  } // 完成后清理
}
```

> **两层各自解决什么**：`pendingFetch` 管"同一时刻"的并发（微任务层面的合并）；`lastFetchedAt + TTL` 管"一段时间内"的跨页冗余（页面 A 拉过，60s 内切到页面 B 不再拉）。
>
> **为什么 filtered 不写缓存**：过滤结果是瞬态数据，缓存它容易过期失真；且原来带 filters 会先发全量再发过滤两次请求，治理成**只发一次条件请求**。

#### 附加亮点：撤回状态的前端持久化

后端撤回语义是把记录置回草稿（`status=0`、可编辑），但产品要求撤回后**不可再编辑**。方案：本地维护 `withdrawnIds` 写入 localStorage，每次重拉列表用 `applyWithdrawnMarks()` 强制标回「已撤回、不可编辑、可删除」——在后端语义不变的前提下兜住前端交互契约。

### 4.4 【架构】useApplicationForm —— 泛型消灭 10 处重复

**代码位置**：`src/shared/composables/useApplicationForm.ts`（唯一作者）

#### 背景

10 个申报模块（读书报告/证书/竞赛/创新/实习/组织/科研/奖学金/实践/培训）结构高度同构：reactive 表单 + 必填校验 + 提交 loading 锁 + 成功提示 + 重置，每处约 170 行复制粘贴代码。

#### 方案

```typescript
export interface ApplicationFormOptions<T> {
  emptyForm: () => T // 空表单工厂：重置逻辑统一
  requiredFields?: (keyof T & string)[] // 必填字段声明式配置
  onSubmit?: (form: T) => Promise<void> | void // 默认走 submitApplication
  type?: string
  typeLabel?: string // 申报类型标识/中文名
  successMessage?: string
}

export function useApplicationForm<T extends Record<string, any>>(opts) {
  const form = reactive(emptyForm())
  const submitting = ref(false) // 提交中状态锁（防重复提交）

  function validateRequired(): boolean {
    const emptyFields = requiredFields.filter((key) => {
      const value = form[key]
      if (value == null || value === '') return true
      if (Array.isArray(value) && value.length === 0) return true // 空数组也算空
      return false
    })
    if (emptyFields.length > 0) {
      ElMessage.warning('请填写所有必填项后再提交')
      return false
    }
    return true
  }

  async function handleSubmit() {
    if (submitting.value) return // 双击防护
    if (!validateRequired()) return
    submitting.value = true
    try {
      await onSubmit(toRaw(form) as T) // toRaw：剥离响应式代理再提交
    } finally {
      submitting.value = false
    }
  }
  // ...
}
```

> **为什么用泛型**：每个模块的表单结构不同（`T extends Record<string, any>`），泛型让 `form.name`、`form[key]` 在使用侧保留完整类型提示，而不是 `any` 一路裸奔。
>
> **为什么 `toRaw(form)`**：reactive 代理对象直接序列化会携带 Proxy，`toRaw` 取回原始对象再交给 API 层，也避免把响应式引用泄漏出组件边界。
>
> **效果**：每个申报模块减少约 170 行重复代码，且校验规则变更只改一处。

### 4.8 【治理】错误提示体系全量审查与修复 —— 拦截器中心化 + 全局兜底

**代码位置**：`src/shared/api/request.ts`（拦截器）、`src/main.ts`（全局兜底）、`docs/2026-09-08-错误提示实现审查报告.md`（审查报告）

#### 背景：一次系统性审查发现了什么

对全项目错误提示做静态审查 + 调用链追踪，按 P0→P2 分级，核心问题是**错误提示的出口不唯一**：

| 级别  | 问题类型       | 数量 | 典型危害                                           |
| ----- | -------------- | ---- | -------------------------------------------------- |
| 🔴 P0 | 失败伪造成功   | 4 处 | 用户看到「已保存」但后端没收到，刷新后数据消失     |
| 🟠 P1 | 双重错误提示   | 6 处 | 拦截器弹一条、组件再弹一条，用户看两条 toast       |
| 🟠 P1 | 查重静默放行   | 1 处 | 查重服务挂了用户无感知，直接提交可能重复           |
| 🟡 P2 | 无全局兜底     | 1 处 | 组件渲染错误 / 未处理 Promise rejection 无任何提示 |
| 🟡 P2 | 校验级别不统一 | 3 处 | 同一「密码不一致」三处用了 error/warning 两种级别  |

#### 方案一：拦截器作为唯一错误 toast 出口

架构原则：**所有经 `request` 实例发出的请求，失败时错误提示由拦截器统一弹，组件 catch 只管状态回滚、不弹 toast**。

```typescript
// 组件层正确写法（teacher 模块主流）
try {
  await submitApplication(data)
} catch {
  /* 拦截器已提示 */
  // ← 只回滚状态，不弹 toast
}
```

> **为什么这是对的**：拦截器拿到的是后端原始 `message`（含具体失败原因），组件硬编码的「提交失败」没有增量信息。两条 toast 纵向堆叠反而稀释了关键信息。

#### 方案二：4 处 P0 假成功的根因与修复

**根因模式统一**：`try { await api() } catch { /* 吞错 */ }` 后**无条件**执行成功逻辑（关弹窗、改本地状态、弹 success）。

| 文件                            | 修复方式                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------ |
| `ProfileInfo.vue`               | catch 中 `return`，不再继续执行 `ElMessage.success('已保存')`                              |
| `review.ts` / `award-review.ts` | 移除 try/catch 吞错，`await` 失败时错误向上抛，不再伪造 `pending` 状态                     |
| `career-plan.ts`                | 删除 `.catch` 中的 Mock 回退 `Promise.resolve(buildRecord(nextId()))`，后端失败直接 reject |

> **教训**：`catch {}` 空捕获是最危险的反模式——它把「失败」伪装成「成功」，且没有任何日志。审查时 grep `catch \{` 重点排查。

#### 方案三：全局错误兜底补齐

```typescript
// main.ts
app.config.errorHandler = (err) => {
  console.error('[GlobalError]', err)
  ElMessage.error('页面出现异常，请刷新重试')
}
window.addEventListener('unhandledrejection', (e) => {
  console.error('[UnhandledRejection]', e.reason) // 只记日志，不弹 toast
})
```

> **为什么 unhandledrejection 不弹 toast**：请求层的 rejection 已由拦截器弹过提示，如果这里再弹会重复。组件渲染错误（errorHandler）才是真正的「兜底提示」场景。

#### 方案四：404 的特殊处理——静默降级

拦截器对 404 **不弹 toast**（[request.ts](../src/shared/api/request.ts)），因为 404 通常意味着「接口未实现」或「数据不存在」，弹错误反而干扰。需要提示的场景在组件层判断：

```typescript
} catch (e) {
  // 404 走拦截器静默降级，此处兜底提示；其余错误拦截器已统一提示
  if (e?.response?.status === 404) {
    ElMessage.error('详情加载失败')
  }
}
```

#### 结果

提交「2026/09/08-前端-错误提示审查报告落地修复」（50 文件 +1,950/-290），错误提示出口收敛为「拦截器 + 全局 errorHandler」双出口，P0/P1 缺陷清零。

## 五、高频追问 Q&A（模拟考官视角）

**Q1：为什么刷新令牌要做成单飞？不做会怎样？**
并发 401 时（首屏十几个请求很常见），每个都触发 `/auth/refresh`。后端 refreshToken 是一次性的，第一个成功后其余全部失败 → 全体 forceLogout，用户"莫名被登出"。单飞让同一时刻只有一个刷新请求，其余复用其 Promise 结果。

**Q2：重试计数为什么挂在 `error.config` 上，不用全局变量或 Map？**
每条请求的重试预算应当独立。axios 重试时 `request(error.config)` 原样传递 config 对象，它天然是"随请求生命周期走"的载体——不需要额外维护 Map 的 key 和清理时机。全局计数器会让 A 请求的重试耗尽 B 的配额。（权衡：axios 类型未扩展该字段，用了 `as any` 并注释，属于已知技术债。）

**Q3：登出接口为什么要排除在 401 刷新链外？**
两个场景：① 账号已在服务端删除/会话已过期时登出返回 401，若触发刷新 → 刷新也 401 → 再登出 → 死循环；② 正常登出本来就是要清会话，此时"续命"逻辑没有意义。排除后登出失败只静默清本地。

**Q4：匿名 401（请求没带 Authorization 却返回 401）说明什么？**
说明该接口需要登录态但前端以匿名方式访问了（如设计为公开、后端白名单未放行）。这不是"令牌过期"——没有令牌可刷。正确处理是下抛给调用方 catch 静默，若走 forceLogout 会整页 reload 且反复触发（150ms 一次的 reload 死循环就是这么来的）。

**Q5：Store 去重为什么需要两层？TTL 缓存会不会导致数据不新鲜？**
`pendingFetch` 解决并发（同一时刻合并），`lastFetchedAt + 60s TTL` 解决跨页冗余（时间维度）。新鲜度问题：提供 `force = true` 参数强制穿透缓存（下拉刷新/ mutation 后重拉都走 force），默认导航进页面用缓存换体验。

**Q6：带筛选条件时为什么只发一次请求？原来是什么问题？**
原来 fetchRecords(filters) 先拉全量再发条件请求，两次网络往返且全量结果被过滤结果覆盖浪费。治理后：filtered 只发条件请求且**不写全量缓存**（瞬态数据不缓存，避免失真）；只有无条件的全量请求才更新 `records` 与时间戳。

**Q7：成长时间轴后端不可用时页面会白屏吗？**
不会。`loadBackendTimeline` 失败时 `backendLoaded = false`，`rebuildExperiences` 的合并基准回退到内置示例数据 `INITIAL_EXPERIENCES`，再拼上用户本地新增的经历——联调期后端不稳定时前端仍可完整演示。

**Q8：双 rAF 那个动画坑，具体是什么机制？**
元素初始 `opacity:0`，回调里直接置 `visible` 时，浏览器可能把"初始态"和"过渡态"合并在同一帧渲染，等于跳过了过渡。两层 `requestAnimationFrame` 强制先提交一帧初始态，下一帧再变更属性，过渡才可见。另外项目滚动根不是 window 而是 `.layout__content`，IntersectionObserver 必须显式传 `root`，否则永远不触发——这是当时"动画丢失"的主因之一。

**Q9：useApplicationForm 里 toRaw 是干什么的？**
reactive 返回的是 Proxy 代理。直接把代理传给 API 层：序列化开销大、可能把响应式系统泄漏到组件边界外。`toRaw(form)` 取回原始普通对象再提交。

**Q10：为什么 CI 要 `--max-warnings 0`？**
警告零容忍才能防止"今天一个 warning，半年后一千个"的规范腐化。警告即阻断合并，倒逼提交前本地修复；配合 husky 的 lint-staged，大部分问题在提交前就被自动 fix。

**Q11：撤回后为什么前端要自己维护 withdrawnIds？**
后端撤回的实现是把记录置回草稿（可编辑），但产品语义要求"撤回=终止本次申报，不可再编辑"。前后端语义暂时不一致时，前端用 localStorage 持久化撤回 ID 列表，每次重拉数据后 `applyWithdrawnMarks` 强制修正状态——这是一个**后端不动、前端兜住交互契约**的过渡方案。

**Q12：你这个项目有什么不足？**（主动示弱版）
① 无自动化测试，验证依赖 `vue-tsc` + build + 人工回归，像 401 死循环这种问题如果有 E2E 会更早暴露；② request.ts 的 `refreshCount` 用了 `as any`，正解是给 axios 模块做 declaration merging 扩展类型；③ 部分接口保留了 Mock 回退双链路，联调期是优点、长期是维护负担；④ 时间轴的能力成长值有前端按类型推断的兜底逻辑，理想态应全部来自后端能力雷达数据。

**Q13：你怎么发现项目里有「失败伪造成功」这种问题的？审查方法论是什么？**
先画调用链：组件 → store → API → 拦截器，确认每个环节错误如何传播、提示归属。然后 grep 三种反模式：① `catch \{` 空捕获后是否有无条件 success；② `catch` 里弹了 error 但后面没 return；③ `.catch` 返回 `Promise.resolve(...)` 把失败变成功。对每处疑似问题做「断网复现」推演：F12 勾选 Offline → 触发操作 → 观察 toast 序列与状态变化。最终产出分级审查报告（P0 误导用户 > P1 体验问题 > P2 一致性）。

**Q14：为什么错误提示要由拦截器统一弹，组件不弹？**
三个理由：① **信息质量**：拦截器拿到后端原始 `message`（含具体原因），组件硬编码的「提交失败」没有增量信息；② **一致性**：全项目错误文案、级别、展示方式统一，不会出现 A 页面红色 error、B 页面黄色 warning 对同一类错误；③ **可维护**：错误策略变更（如加日志上报、调整文案）只改拦截器一处。代价是组件需要知道「哪些 API 走拦截器、哪些绕过（如 blob 下载）」，绕过的才需要组件层提示。

**Q15：那组件层完全不弹错误提示吗？什么时候该弹？**
两种情况组件层必须弹：① **绕过拦截器的请求**（如原生 axios + blob 下载文件），拦截器不会处理，组件必须自己提示；② **前端本地校验失败**（如「两次密码不一致」「必填项未填」），这类错误没发请求、拦截器无从介入。其余走 `request` 实例的请求，组件 catch 只做状态回滚，不弹 toast。

**Q16：404 为什么拦截器选择静默不弹 toast？**
404 的语义是「资源不存在」，在前端项目里通常意味着两种情况：① 后端接口尚未实现（联调期常见）；② 查询的记录已被删除。两种情况都不适合弹错误 toast——前者会持续骚扰开发者，后者用户已经离开该记录上下文。静默降级后由组件层根据场景决定：列表页展示空态，详情页在 catch 里判断 `e.response.status === 404` 再弹「详情加载失败」。

**Q17：全局 errorHandler 和 unhandledrejection 有什么区别？为什么一个弹 toast 一个不弹？**
`app.config.errorHandler` 捕获的是**组件渲染/生命周期错误**（如模板里访问 undefined 属性、onMounted 抛异常），这类错误用户感知到的是页面白屏或交互失效，必须给提示。`unhandledrejection` 捕获的是**未处理的 Promise rejection**，但请求层的 rejection 已经被拦截器弹过 toast 了，如果这里再弹会重复。所以 unhandledrejection 只记日志用于排查，不弹 toast——真正需要兜底的是请求层之外的异步错误（如定时器、第三方库回调里的 Promise）。

**Q18：「失败伪造成功」的根因是什么？怎么在 Code Review 中快速识别？**
根因是 `try/catch` 中 `catch` 吞掉了错误但没有控制流中断（return/throw），导致后续成功逻辑无条件执行。CR 快速识别法：看 `try` 块后的代码是否依赖 `try` 成功——如果 `catch` 后还有改状态、弹 success、关弹窗，且 `catch` 里没有 `return`，就是高危。grep 关键词：`catch \{` 后紧跟非 `return`/`throw` 的代码、`catch \{\s*/\*` 空捕获。

**Q19：为什么查重接口失败选择「放行 + warning 提示」而不是「阻止提交」？**
产品语义上查重是**辅助校验**而非**强制门槛**——查重服务故障不应阻塞正常申报流程。但静默放行会让用户误以为已完成查重，存在重复提交风险。折中方案：放行保证业务可用，`ElMessage.warning('查重服务暂不可用，本次未执行重复检测')` 明确告知用户降级状态，用户知情后可自行决定是否继续。这是「可用性 > 严格性」的典型权衡。

**Q20：密码一致性校验为什么用 warning 而不是 error？**
这是**前端本地校验**（还没发请求），属用户输入问题而非系统错误。`warning`（黄色）传达「请修正输入」的引导语气，`error`（红色）传达「操作失败」的结果语气。统一用 warning 的好处：与表单必填校验、格式校验的提示级别一致，用户形成「黄色=我需要改输入」的稳定预期。
