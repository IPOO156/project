## 三、错误处理架构概述

### 3.1 架构模式：拦截器中心化 ✅

[request.ts](../src/shared/api/request.ts) 是全局唯一的错误 toast 出口，三层错误链全覆盖：

```
请求 → 响应拦截器
  ├─ 业务错误（code ≠ 0/200）→ ElMessage.error(后端 message || '请求失败')   [L87-94]
  ├─ HTTP 状态码分支                                                    [L125-154]
  │    ├─ 401 → 刷新令牌重试链（单飞去重 + 最多 3 次 + 业务 401 排除 + 匿名 401 下抛）
  │    ├─ 403 → '没有权限执行此操作'
  │    ├─ 429 → '请求过于频繁，请稍后重试'
  │    ├─ 500 → '服务器异常，请稍后重试'
  │    ├─ 404 → 静默降级（不弹，交调用方处理空态）                        [L149-151]
  │    └─ default → 后端 message || '网络错误'
  └─ 网络层 → 超时 '请求超时，请检查网络' / 断网 '网络异常，请检查网络连接'  [L155-158]
```

### 3.2 架构亮点（符合规范的部分）

1. **展示方式统一**：全项目 `ElMessage.error` 唯一出口，`ElNotification` 零使用，无样式覆盖（`src/assets/` 内 `el-message` 零命中）
2. **401 刷新链健壮**：`refreshPromise` 单飞去重（[L33-64](../src/shared/api/request.ts#L33-L64)）、`refreshCount` 最多 3 次（[L110](../src/shared/api/request.ts#L110)）、业务 401 排除（登录/改密/登出，[L79-83](../src/shared/api/request.ts#L79-L83)）、匿名 401 直接下抛防 reload 死循环（[L105-109](../src/shared/api/request.ts#L105-L109)）、`forceLogout` 防死循环（[L66-75](../src/shared/api/request.ts#L66-L75)）
3. **信息来源合理**：优先取后端 `message`，前端硬编码中文兜底，不暴露堆栈/SQL，符合 CLAUDE.md 3.4 第 3/4 类要求
4. **团队约定明确**：67 处组件 `catch { /* 拦截器已提示 */ }` 注释证明「拦截器弹错、组件只管状态回滚」是自觉约定，teacher 模块执行最彻底
5. **文件下载绕过拦截器是刻意设计**：`downloadGradeImportTemplate` / `downloadSemesterImportTemplate`（[teacher.ts:534](../src/shared/api/teacher.ts#L534)、[teacher.ts:900](../src/shared/api/teacher.ts#L900)）用原生 axios + blob 绕过 JSON 拦截器，组件层 `'模板下载失败'` 是唯一提示，做法正确

### 3.3 规范差距

CLAUDE.md 3.4 要求「前后端均需对异常进行日志记录和监控告警」，前端未落地：无 `app.config.errorHandler`、无 `unhandledrejection` 监听、无 `onErrorCaptured`（详见 §5.7）。

## 四、P0 问题详情（失败伪造成功，直接误导用户）

### 4.1 个人信息保存：失败与成功提示并存

**位置**：[ProfileInfo.vue:146-167](../src/features/profile/ProfileInfo.vue#L146-L167)（`saveEdit()`）

**根因**：政治面貌/学生状态更新（透传 `request.put`，[student.ts:211-224](../src/shared/api/student.ts#L211-L224)）失败进入 catch 弹错后**未 return**，继续执行 `isEditing.value = false` 与 `ElMessage.success('已保存')`（L166）。而拦截器在 catch 之前已先弹过一条后端错误 message。

**复现步骤**：

1. 学生账号登录，进入个人信息编辑页（`src/features/profile/ProfileInfo.vue`）
2. F12 → Network → 勾选 `Offline`（手段 A）
3. 点击「编辑」，将**政治面貌**改为任意不同值
4. 点击「保存」
5. 观察顶部 toast 序列（注意堆叠，勿等前一条消失）

**预期**：仅一条错误提示（如「保存失败，请重试」），编辑框保持打开、表单值保留
**实际**：

| 序号 | toast                                              | 来源      |
| ---- | -------------------------------------------------- | --------- |
| 1    | 『网络异常，请检查网络连接』（或后端错误 message） | 拦截器    |
| 2    | 『学籍信息保存失败』                               | 组件 L161 |
| 3    | 『已保存』（绿色成功）                             | 组件 L166 |

且编辑框已关闭、界面回读旧值，但用户被告知「已保存」。

**修复建议**：catch 块中 `ElMessage.error('学籍信息保存失败')` 后立即 `return`，终止后续的关闭编辑框、`fetchArchive()` 与成功提示；同时删除组件层冗余提示（拦截器已弹过后端 message）。

### 4.2 审核记录重新提交：接口失败伪造待审核状态

**位置**：[review.ts:112-130](../src/app/stores/review.ts#L112-L130)（`resubmit()`）；调用入口 [ReviewDialog.vue:79](../src/features/approval/components/ReviewDialog.vue#L79)

**根因**：`updateActivity` 失败被 `catch { /* 接口失败时本地更新 */ }` 吞掉（L115-117），随后无条件执行本地状态伪造为 `pending`（L119-127）并弹 `ElMessage.success('修改已保存，等待重新审核')`（L129）。后端实际未收到修改。

**复现步骤**：

1. 学生账号登录，确保存在一条**已退回**的动态记录（可先由教师端退回一条）
2. F12 → Network → Network 面板 → 右键任意 `activities` 相关请求 → `Block request URL`（拦截 `**/activities/**`，手段 B）
3. 进入审核记录页，打开该退回记录的编辑弹窗（`ReviewDialog.vue`）
4. 修改任意内容后点击「提交」
5. 观察 toast 与列表状态
6. **按 Ctrl+F5 强制刷新**，再次观察该记录状态

**预期**：仅拦截器弹一条错误提示，记录状态保持「已退回」
**实际**：

- 提交瞬间：错误 toast 与『修改已保存，等待重新审核』**同时出现**
- 列表中该记录状态变为「待审核」（前端伪造）
- 刷新后状态复原为「已退回」——证明后端从未收到修改，此前的「待审核」为假状态

**修复建议**：catch 后直接 `throw`（或 `return`），删除本地状态伪造与成功提示，交由拦截器提示；刷新列表恢复真实状态。

### 4.3 奖项审核记录重新提交：同款反模式

**位置**：[award-review.ts:52-61](../src/app/stores/award-review.ts#L52-L61)；调用入口 [StarDialog.vue:169](../src/features/approval/components/StarDialog.vue#L169)

**根因与修复**：与 §4.2 完全相同，仅数据域不同（award）。

**复现步骤**：同 §4.2，将入口换成奖项申报记录的编辑弹窗（`StarDialog.vue`）。

### 4.4 职业规划提交：API 层 Mock 回退伪造成功

**位置**：[career-plan.ts:105-110](../src/shared/api/career-plan.ts#L105-L110)（`submitCareerPlan` 的 catch）；组件侧 [CareerPlan.vue:139-159](../src/features/profile/CareerPlan.vue#L139-L159)

**根因**：`submitCareerPlan` 的 catch 仅对**前端本地错误**（「未找到学期」）reject，**后端真实失败一律 resolve Mock 假记录**。组件层 catch（L155-156）只在前者触发（此时拦截器未弹过提示，组件提示是唯一提示，合理）；后者直接走到 L154 `ElMessage.success('规划已提交')`。

**复现步骤**：

1. 学生账号登录，进入成长发展页（`src/features/profile/CareerPlan.vue`）
2. F12 → Network → 勾选 `Offline`（手段 A）
3. 填写规划表单（学期、标题、内容等）后点击「提交」
4. 观察 toast 与列表

**预期**：仅一条错误提示，列表不新增记录
**实际**：

- 网络错误 toast 与『规划已提交』（绿色成功）**同时出现**
- 列表新增一条假记录（id 为本地自增 `nextId()`）
- 刷新后假记录消失（后端从未收到）

**补充场景**：若要单独验证「未找到学期」分支（组件提示为唯一提示，属合理路径），可在学期下拉中构造一个后端不存在的学期值后提交——此时仅弹『提交失败』一条。

**修复建议**：移除 catch 中的 Mock 回退（`return Promise.resolve(buildRecord(nextId()))`），后端失败时直接 reject 交由拦截器提示、组件 catch 只做状态回滚；「未找到学期」错误建议改为 `ElMessage.warning` 级别的明确文案。

**通用复现步骤**（以 #1 为例，其余替换入口即可）：

1. 学生账号登录，进入任一申报页（如奖学金申报）

**特例说明**（#5）：`getCareerPlanDetail` 若失败状态码为 404，拦截器静默（[request.ts:149-151](../src/shared/api/request.ts#L149-L151)），组件的『详情加载失败』为唯一提示，属合理兜底；非 404 失败即为双重提示。

**修复建议**：统一改为 teacher 模块主流写法 `catch { /* 拦截器已提示 */ }`；若需更具体提示，参照 [ProofUpload.vue:102-108](../src/shared/ui/ProofUpload.vue#L102-L108) 的防重复弹窗守卫——检查 `e.response?.data?.message || e.message` 无值时才兜底 toast。

### 5.2 查重接口失败静默放行

**位置**：[useApplicationPage.ts:175-177](../src/shared/composables/useApplicationPage.ts#L175-L177)

**根因**：`checkDuplicateBeforeSubmit` 的 catch `return true` 直接放行提交。接口涉及 `POST /applications/duplicate-check`（档案申报）与 `POST /awards/duplicate-check`（奖项报名）。

**复现步骤**：

1. 学生账号登录，进入任一申报页
2. F12 → Network → 右键查重请求 → `Block request URL`（拦截 `**/duplicate-check`，手段 B）。**注意：不要用 Offline**，否则后续提交也会失败，无法观察放行效果
3. 填写完整表单后点击「提交」
4. 观察 Network 面板与页面提示

**预期**（至少二选一）：查重失败时提示「查重服务暂不可用，已跳过查重」之类的降级说明；或阻止提交
**实际**：查重请求显示红色失败，页面**无任何提示**，静默进入提交流程

**修复建议**：保留放行策略（避免查重故障阻塞业务）但增加 `ElMessage.warning('查重服务暂不可用，本次未执行重复检测')` 降级提示，或至少 `console.warn` 留痕。

### 5.3 密码一致性校验提示级别不统一

2. 场景二：学生端个人中心 → 修改密码 → 两次输入不同 → 提交 → 观察 toast 为**红色 error**

### 5.4 无全局错误兜底

**位置**：[main.ts](../src/main.ts)（无 `app.config.errorHandler`）；全 src 无 `unhandledrejection` / `onErrorCaptured`

**复现步骤**：

1. 任一页面 F12 → Console 执行：

```js
Promise.reject(new Error('test-unhandled'))
```

2. 观察页面与 Console

**预期**：存在全局兜底时应有统一处理（如统一 toast + 日志上报）
**实际**：仅 Console 出现 `Uncaught (in promise)` 红字，页面无任何用户提示；组件渲染错误同理依赖浏览器默认行为

**修复建议**：在 `main.ts` 补充（约 10 行）：

```ts
app.config.errorHandler = (err) => {
  console.error('[GlobalError]', err)
  ElMessage.error('页面出现异常，请刷新重试')
}
window.addEventListener('unhandledrejection', (e) => {
  console.error('[UnhandledRejection]', e.reason)
})
```

### 5.5 无环境差异化配置

**现状核查**（`Get-ChildItem .env*` 零命中）：

- 项目根目录无任何 `.env` 文件；`import.meta.env` 无实际消费
- `baseURL: '/api/v1'` 与 `timeout: 15000` 硬编码于 [request.ts:10-18](../src/shared/api/request.ts#L10-L18)
- 代理 target 硬编码于 `vite.config.js`（内网穿透地址），仅 dev 生效；生产依赖部署侧反向代理

**建议**：属工程配置项而非 bug，可后置。如需区分，引入 `.env.development` / `.env.production` 管理 `VITE_API_BASE_URL` 与 `VITE_DEBUG`。
