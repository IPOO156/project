# 成长时间轴事件未归集学期 —— 后端问题描述与改造建议（2026-11-06）

> 用途：前端已按「学期只认后端」整改完毕，但后端当前没有归集逻辑，导致新增/历史事件的学期为空。
> 本文用于与后端对齐口径：**由后端按 `event_at` 匹配 `semesters.start_date ~ end_date` 回填 `semester_id`**，前端只消费 `semesterName`。
>
> 前端定位：`src/features/growth-timeline/`；相关修改记录见 `代码修改记录/2026-11-06.md`。

## 一、问题概述

成长时间轴事件（`growth_timelines`）的学期字段 `semester_id` 目前没有任何服务端归集逻辑：

- 新增/修改接口的 `semesterId` 是**可选**字段：传了就 `validateSemester()` 校验存在后原样落库，不传就存 `null`；
- 查询响应中的 `semesterName` 只是 `semester_id` 反查 `semesters.name`，`semester_id` 为 `null` 时返回 `null`；
- 学期表 `semesters` 已有 `start_date` / `end_date`（以及 `is_current`），但只用于下拉与「当前学期」标记，没有「按日期归学期」的查询或计算。

前端此前用 `inferSemester()` 按「9 月为学年起点」自行推断学期，导致两个问题：

1. 与学校在学期管理中维护的真实起止日期无关（如 8 月底开学、1 月中旬放假时会算错）；
2. 前端新增事件时**没有提交 `semesterId`**，落库后 `semester_id` 一直为 `null`，后端永远返回不出学期。

前端已于本次整改中删除全部本地推导（`inferSemester` 及回退逻辑），因此现在后端不归集，事件就没有学期可展示，也不会出现在年轮对应位置。

## 二、事实依据（后端代码位置）

| 位置                                                         | 现状                                                                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `GrowthTimeline` 实体（`entity/growth/GrowthTimeline.java`） | `@Column(name = "semester_id") private Long semesterId;`，无 `nullable = false`，允许为空                                           |
| `ProfileGrowthTimelineService.create()`                      | `if (request.getSemesterId() != null) validateSemester(...)`；随后 `timeline.setSemesterId(request.getSemesterId())`，未传即 `null` |
| `ProfileGrowthTimelineService.update()`                      | 同上，`semesterId` 传了才更新，没有推导                                                                                             |
| `ProfileGrowthTimelineService.toDetail()`                    | `semesterId(timeline.getSemesterId())`、`semesterName(semesterName(timeline.getSemesterId()))`，为空时返回 `null`                   |
| `Semester` 实体（`entity/org/Semester.java`）                | 已有 `startDate` / `endDate` / `isCurrent` 字段，具备归集条件                                                                       |
| `SemesterRepository`                                         | 只有 `findActiveBySchoolId`（按 `start_date` 倒序）与 `findCurrentBySchoolId`（`is_current=1`），没有日期区间匹配方法               |

## 三、影响范围

- **学生端成长时间轴**：新增经历后卡片、详情、列表均不显示学期；年轮视图无法把该事件放到对应学期圈层（前端已改为「无学期不渲染」，不会再错画到「大一上」）。
- **历史数据**：所有通过前端新增且未传 `semesterId` 的事件（预计占绝大多数）`semester_id` 均为 `null`。
- **其他读取 `growth_timelines` 的模块**：凡依赖 `semester_id`/`semesterName` 的统计、导出、时间轴筛选都会漏掉这些事件。

## 四、期望行为（建议口径）

### 4.1 新增 / 修改时归集

在 `ProfileGrowthTimelineService.create()` 与 `update()` 中：

1. 若请求显式传了 `semesterId`：保持现有逻辑，校验存在后使用；
2. 若未传且 `eventAt` 有值：按「同校 + 启用 + 未删除 + `start_date <= eventAt <= end_date`」查询唯一学期，命中则写入 `semester_id`；
3. 未命中（如寒暑假、学期表未维护的日期）：**保持 `null`，不要猜测、不要报错**（与前端「不编造」口径一致）；
4. 学期需限定 `school_id = user.schoolId`、`status = 1`、`deleted_at IS NULL`，避免跨校或停用学期；
5. 若存在多个区间重叠的学期：以后端学期管理的「日期不重叠」校验为准；如历史数据确有重叠，取 `start_date` 最晚的一条并记录告警日志。

`update()` 中若修改了 `eventAt` 且请求未显式带 `semesterId`，应按新日期重新归集；若请求显式带了 `semesterId`，以请求为准。

### 4.2 查询响应

`GET /profile/growth-timeline`（列表）与 `GET /profile/growth-timeline/{id}`（详情）保持现有字段，`semester_id` 有值时返回：

```json
{
  "semesterId": 12,
  "semesterName": "2025-2026-2"
}
```

`semesterName` 用 `semesters.name`（如 `2025-2026-2`），不要返回 `label`，前端已有 `useSemesterRings` 负责展示成「大二下」。

### 4.3 历史数据回填（一次性 SQL）

```sql
UPDATE growth_timelines gt
JOIN semesters s
  ON s.school_id = gt.school_id
 AND s.status = 1
 AND s.deleted_at IS NULL
 AND s.start_date IS NOT NULL
 AND s.end_date IS NOT NULL
 AND gt.event_at BETWEEN s.start_date AND s.end_date
SET gt.semester_id = s.id
WHERE gt.semester_id IS NULL
  AND gt.deleted_at IS NULL;
```

> 执行前先 `SELECT COUNT(*)` 核对命中量，并确认 `semesters` 无重叠区间；执行后抽查若干事件的 `semester_id` 是否落在正确学期。

## 五、验收标准

| #   | 场景                                                                     | 期望                                                             |
| --- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 1   | 新增事件 `eventAt = 2025-10-15`，学期表存在 `2025-2026-1`（9/1~1/31）    | 落库 `semester_id` 为该学期；响应 `semesterName = "2025-2026-1"` |
| 2   | 新增事件 `eventAt` 为学期表未覆盖的日期（如 2025-08-15）                 | `semester_id = null`，接口正常成功，不报错                       |
| 3   | 修改事件日期跨学期（如从 2025-10-15 改为 2026-03-01）且未传 `semesterId` | `semester_id` 重新归集为 `2025-2026-2`                           |
| 4   | 请求显式传 `semesterId`                                                  | 以请求值为准（仍校验存在）                                       |
| 5   | 历史数据回填后查询旧事件                                                 | 原本 `semester_id` 为空的事件能返回正确的 `semesterName`         |
| 6   | 停用学期 / 其他学校学期                                                  | 不会被匹配到                                                     |

## 六、前端现状（无需再改）

- 已删除 `inferSemester()` 及所有回退；表单不再展示「自动推导」的学期。
- 事件学期只取后端 `semesterName`；为空时卡片/列表/详情不渲染学期徽章，年轮不放置该事件（避免错画到「大一上」）。
- 后端上线归集并回填后，前端无需改动即可显示学期。

## 七、待后端确认

1. `semesters.end_date` 是否包含当天（建议 `<=`，与 `start_date` 同为闭区间）；
2. 学期表存在 `start_date`/`end_date` 为空的历史学期时，是否允许跳过匹配；
3. 若同一日期命中多个学期（历史脏数据），采用哪种策略（建议取 `start_date` 最晚者 + 告警）；
4. 历史数据回填由后端在本次改造中一并执行，还是单独提供脚本由运维执行。
