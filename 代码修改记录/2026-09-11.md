## 七、追加修改（第二轮：审批委托权限口径修正）

- **需求来源**：产品口径 —— **审批委托只能「管理员 → 教师」，教师不可互相委托**，教师端不应出现「审批委托」模块。
- **前一轮的问题**：第一轮把 `delegation` 模块的权限码写成 `['delegate:manage', ADMIN_MENU_CODE]`，而 `delegate:manage`（种子 id=36）在 `seed_teachers.sql` 中同时授予了 teacher(3) 与 counselor(4)，导致教师/辅导员被放出了「审批委托」菜单 —— **与业务口径相反**。
- **后端核查结论**（只读，未改动后端）：
  1. `TeacherDelegationController`（`/teacher/delegations`）**未做任何权限码校验**，`/teacher/**` 在 `SecurityConfig` 中仅要求 `authenticated`；而该 Controller 的 Javadoc 却标注「权限码：delegate:manage」—— **文档与实现不一致，任何登录用户均可调用**。
  2. `TeacherDelegationService.createDelegation` 的 `delegatorId` 取自 `@AuthenticationPrincipal`（当前登录人），并校验「委托人必须持有该 roleId + 范围覆盖」——即实现的是**「自己把自己的审批角色/范围委托出去」**，天然允许教师→教师；教师端页面创建时**不传 roleId**，恰好绕过角色校验。
  3. `seed_admins.sql` 中 admin(role 2) 的授权为权限 id 8~23 + 37，**不含 36（delegate:manage）**；`seed_teachers.sql` 反而把 36 授予了 teacher/counselor —— **种子授权方向与业务口径正好相反**。
  4. `DelegationManage.vue` 的「被委托人」下拉调用管理端 `GET /admin/users`，该接口要求 `user:view` / `user:manage` 权限码或 admin 角色；教师两者都不持有 → **教师打开该页时下拉必然 403，本就无法完成委托**（属改造前就存在、但因菜单未放出而未暴露的缺陷）。

## 十一、追加修改（第六轮：dev server 端口漂移导致登录 403 的根因定位与硬约束）

**触发**：用户报「登录管理员账号报没有权限执行此操作」，抓包为 `POST http://localhost:5174/api/v1/auth/login` → **403 Forbidden**；随后补充「目前我不管登陆什么账号都显示没有权限执行此操作」。

### 11.0 根因（结论：与账号、角色、权限码均无关）

**403 由后端 Spring 的 CORS 处理器在进入 Controller 之前返回，请求体为 `Invalid CORS request`。**

排查路径与证据：

1. **排除业务层**：`AuthController.login`（`controller/Fmy/AuthController.java:60`）除 `@Valid @RequestBody` 外**无任何鉴权注解**；`AuthService.login()`（`service/Fmy/AuthService.java:135-240`）全文**无 `ACCESS_DENIED` / `FORBIDDEN`**，其失败分支仅为验证码→`PARAM_ERROR`(400)、限流→`TOO_MANY_REQUESTS`(429)、查无此人/禁用/密码错→`PASSWORD_ERROR`(401)。**登录方法本身产不出 403。**
2. **排除鉴权链**：`/auth/login` 是 `SecurityConstants.PUBLIC_AUTH_PATHS` 的**第一项** → `permitAll`；`JwtAuthenticationFilter.shouldNotFilter()`（`config/security/JwtAuthenticationFilter.java:54-67`）对该路径返回 `true` → **过滤器整体跳过**；且该过滤器内部所有分支（未登录/登录过期/Token 无效/类型错/用户不存在/账号禁用）均为 **401 族，无一条 403**。
3. **定位到 CORS 层**：直连部署后端做 Origin 矩阵实测（同一空 body 请求，无凭据，仅改 `Origin` 头）：

   | `Origin`                | 实测结果                                                                          |
   | ----------------------- | --------------------------------------------------------------------------------- |
   | `http://localhost:5173` | ✅ 进入 Controller → `{"code":10001,"message":"学号不能为空；验证码不能为空；…"}` |
   | `http://localhost:5174` | ❌ **403 `Invalid CORS request`**                                                 |
   | `http://localhost:5175` | ❌ **403 `Invalid CORS request`**                                                 |
   | 不带 Origin             | ✅ 进入 Controller                                                                |

   后端 `config/WebConfig.java:57-68` 的 CORS 白名单（`ALLOWED_ORIGINS`）只含 `3000 / 5173 / 8080`。

4. **为何「换任何账号都一样」**：403 在 Controller 之前返回，**服务端根本没读到账号**，故与账号/角色/密码无关 —— 这一现象本身即是 CORS 层拒绝的决定性证据（若是权限码问题，admin 走 `AdminAuthService` 角色直通必然放行）。
5. **前端为何显示「没有权限执行此操作」**：`src/shared/api/request.ts:141` 把**所有** HTTP 403 无差别映射为该固定文案，而 `Invalid CORS request` 是 403 但**与权限无关** —— 该映射把排查引向了权限方向。
