## 3.2 失败归因（已定性）

失败的表面现象统一是：登录后 20s 内未离开 `/login`，报 `expect(page).not.toHaveURL(/\/login/)`。

从 trace（`1-trace.network` / `3-trace.network`）中取得的**决定性证据** —— 失败那一刻**所有** API 请求同时 500：

| 请求                        | 状态 | 响应体    | 耗时  |
| --------------------------- | ---- | --------- | ----- |
| `/api/v1/public/statistics` | 500  | `size: 0` | —     |
| `/api/v1/auth/captcha`      | 500  | `size: 0` | 185ms |
| `/api/v1/auth/login`        | 500  | `size: 0` | 128ms |
| `/api/v1/auth/captcha`      | 500  | `size: 0` | 136ms |

响应头 `Transfer-Encoding: chunked`、`Content-Type: text/plain`、**body 字节数为 0** —— 即既有记录中的「空 body 500」。

进一步区分成因（两者在代理层表现相同，只有直连可鉴别）：

```
直连  http://vf2a39ce.natappfree.cc/api/v1/auth/captcha
  → HTTP 404  body: "Tunnel vf2a39ce.natappfree.cc not found"（40 字节）
经代理 http://localhost:5173/api/v1/auth/captcha
  → HTTP 500  body 字节数: 0
```

**结论：本次失败全部由 natapp 隧道客户端掉线导致**（域名未注册），不是限流。后端根本没收到请求（128ms 空响应）。

# 四、本轮发现的真实问题（非本次失败主因，但应处理）

## 4.1 【测试设计】`beforeAll` 登录是单点故障，一处抖动放大成整组"未执行"

`student.spec.ts:53-58` 与 `teacher.spec.ts` 均在 `test.beforeAll` 中用 `browser.newPage()` 手工建页并登录，失败即导致该组**全部**用例报 `did not run`（学生端 6 个、教师端 5 个）。

后果：报告里出现「12 did not run」这种读数，**无法区分「页面坏了」与「登录那一枪没打通」**，误判风险高。这也是本轮前几次读数看起来像大面积失败的原因。

**建议**：登录改到 `beforeEach`（单个用例约 400ms–3s，代价可接受），让一次抖动只影响一个用例；或保留 `beforeAll` 但在其中对登录做显式重试并给出可读的失败信息。

## 4.2 【覆盖缺口】管理员端零覆盖

`tests/e2e/helpers/login.ts:15` 定义了 `admin: { userNo: 'A00002' }`，但**没有任何 spec 使用它**。管理员身份目前只在登录页那一层被间接涉及，进入系统后的功能完全空白。

另注：前端**没有独立管理员端**，管理员与教师共用 `/teacher/*`，靠 `/auth/me` 的权限码区分菜单，故「三端」实为两端 + 管理员账号。

## 4.3 【既有，未提交】`src/shared/api/teacher.ts` 重复实现验证码跳过逻辑

工作区未提交改动在 `teacherLogin` 内又加了一份 `CAPTCHA_SKIP_SECRET` / `CAPTCHA_SKIP_ACCOUNTS` 与请求头设置，而 `src/shared/api/request.ts:21-39` 的 axios 拦截器**已实现同一逻辑**。常量与白名单两处各定义一份，违反 §2.8 与 CR 清单「是否有未经沟通的重复实现」。功能上不会出错（同值再赋一次），但白名单日后改一处漏一处会出问题。建议回退该段。

另：`request.ts:39` 残留 `console.warn('[Skip Captcha] ...')`，每次登录都会打印，建议删除或降级。
