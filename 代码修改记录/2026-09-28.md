本次排查发现两份配置的 `proxy./api.target` **已经漂移**：

## 三、本次新发现（前端缺陷，待处理，未在本次修改）

**`ScoreIndicatorDialog` 的「权重」列显示的是得分率，且「加权总分」用它参与计算，结果是错的。**

- 数据来源：`src/shared/composables/useScoreIndicator.ts:39-40` 从 `GET /profile/scores` 的 `list[]` 取数，而该接口**只返回** `dimensionCode / dimensionName / score / targetScore / gap / change / unit`，**没有任何权重字段**。前端自行构造：
  ```ts
  maxScore: d.targetScore || 100,
  weight: d.targetScore ? d.score / d.targetScore : 0,   // ← 这是得分率，不是权重
  ```
- 后果一：`ScoreIndicatorDialog.vue` 的「权重」列渲染 `Math.round(item.weight * 100)%`、「得分率」列渲染 `score/maxScore`，**两列显示完全相同的数字**（弹窗实测：40% / 40%、33% / 33%、0% / 0%）。
- 后果二：「加权总分」按 `Σ(score × weight)` 计算，即 `20×0.4 + 10×0.333 + 0×0 = 11.3`，满分按 `Σ(maxScore × weight)` 得 `30.0`，于是弹窗显示 **「加权总分 11.3 / 30.0」**——两个数字均无业务含义（正确口径下权重为 0.5 / 0.3 / 0.2）。学生看到的是一个**算错的分数**。
- 合规性：该写法同时触及 CLAUDE.md §5.2「❌ 伪造接口字段」与 §3.7「禁止前端根据 UI 样式自行编造字段名」——`weight` 并非接口返回字段。
- **处理建议（需先与后端对齐口径）**：由后端在 `GET /profile/scores` 的 `list[]` 中补充真实 `weight` 字段（与 `/profile/scores/{id}/details` 的 `weight` 对齐）；前端在此之前不应自行推导权重，可先将「权重」列改为「满分占比」或暂时隐藏该列，避免继续展示错误数字。**该项未在本次改动，待后端接口确认后另开需求。**

# 需求四：进度条改按「得分率」绘制 + 分值补满分

## 一、背景（问题复现）

需求三验证时发现「档案概览 → 多维度画像」卡片两处口径问题：

1. **进度条把原始分当百分比**：`<el-progress :percentage="dim.score">`。而各维度满分不同（学业成绩 50 / 竞赛实践 30 / 综合素质 20，即权重 ×100），于是「20 / 50」与「20 / 100」会画成一样长的条，维度之间无法横向比较。实测李四：学业成绩 20 分画出 20% 长度（按得分率应为 40%）、竞赛实践 10 分画出 10%（应为 33%）。
2. **分值不显示满分**：只渲染「20分」，学生分不清是 20/50 还是 20/100。

数据本身是齐的：`src/app/stores/archive.ts:89-95` 早已把 `/profile/info` 的 `targetScore` 映射为 `ProfileDimension.target`（见 `src/shared/types/types.ts:69`），只是 `ProfileInfo.vue` 的 `dimensions` computed 没有把它往下传，满分在页面层被丢弃了。

**打桩方式**：`page.route` 拦截 `/api/v1/profile/info`，`route.fetch()` 拿后端真实响应后就地改写 `dimensionProfile` 再 `fulfill`——**只改响应体，不写入任何后端数据**。

两处设计取舍（均已在用例文件内注释说明）：

- **路由只在 `beforeAll` 注册一次、由变量驱动**，而不是每个用例 `page.route` / `unrouteAll`。后一写法会让「用例结束时撤销路由」与仍在处理中的 `/profile/info` 请求竞争，抛 `route.fulfill: Route is already handled!`，请求永远拿不到响应、卡片不渲染（本次实测踩到该坑，故改为单次注册）。
- **刻意不开 `mode: 'serial'`**：配置中 `fullyParallel: false`，同一文件内的用例已按声明顺序在同一 worker 串行执行，共享 `page` 不需要 serial；而 serial 会在首个用例失败后跳过其余用例，导致 3 个与后端数据无关、恒可执行的打桩用例被跳过，丢掉最有价值的诊断信息。

## 一、「综合评分 / 加权总分」口径问题详述

### 1.1 一句话概括

学业成绩 **20 / 50**、竞赛实践 **10 / 30**、综合素质 **0 / 20**——

### 1.3 逐条问题说明

**①②③ 原始分算术平均（三处重复实现）**

- 数学上不成立：各维度满分不同（50 / 30 / 20），对原始分直接求平均，隐含了两个未经确认的前提——「三个维度等权」且「三个维度同尺度」。李四的 10 分既不是 10/100，也不是任何可解释的比率；若三个维度得分各为满分的一半，该口径会给出「(25+15+10)/3 ≈ 17」，而不是直觉上的 50。
- 与同页进度条口径冲突（本次改动的直接后果）：进度条现在画**得分率**（40% / 33% / 0%），而卡片标题栏并排写着「综合评分 10分」。学生看到「三条 40%、33%、0% 的进度条」配「10 分」，两个数字对不上，反而比改之前更刺眼。
- 与后端权重口径冲突：按后端权重 0.5 / 0.3 / 0.2 且 `targetScore = 权重 × 100` 推导，**加权总分（百分制）= Σ(维度得分率 × 维度权重) × 100 = 0.4×0.5 + 0.333×0.3 + 0×0.2 = 0.30 → 30 分**（因 `score = 得分率 × 权重 × 100`，该式恰等于 `Σ score = 30`，满分 100）；**平均得分率 = (40% + 33% + 0%) / 3 ≈ 24%**。算术平均得到的 **10** 与这两者都不相等。
- **③ 的影响面最大**：这段文本会随简历导出、交付给第三方（原文：「在校期间平均绩点 {{ avgGpa }}，综合评分 {{ dimAvg }} 分，专业基础扎实…」）。页面上的错误数字看一眼就过去了，写进简历的数字会被带出系统。
- 三处是**同一公式的重复实现**，也触及 CLAUDE.md §2.6「复用组件前置沟通」与「存在重复逻辑」的 CR 检查项——即便口径最终不改，也应抽成一个工具函数或后端下发。

**④ 弹窗「加权总分」是算错的**（详见「需求三 · 三」，此处只做口径对照）

- 代码算的是 `Σ(得分 × 得分率) / Σ(满分 × 得分率)`：分子 `20×0.4 + 10×0.333 + 0 = 11.3`，分母 `50×0.4 + 30×0.333 + 20×0 = 30.0`，故渲染「加权总分 11.3 / 30.0」。
- 两个数字都没有业务含义。**同一个弹窗里**，「权重」列与「得分率」列之所以显示完全相同的百分比（40%/40%、33%/33%、0%/0%），根因就是「权重」列填的是得分率——即 `useScoreIndicator.ts:39-40` 在 `GET /profile/scores` 未返回 `weight` 时自行构造了 `weight = score / targetScore`。
- 值得注意的是，该弹窗的「计算说明」明细表（`/profile/scores/{id}/details`）**是后端下发的真实 `weight` / `weightedScore`**，同一弹窗内两个表口径不一致。这说明后端在**指标级**已经正确建模了权重，缺的只是 `/profile/scores` 维度级 `list[]` 的 `weight` 字段——修法很小：后端补字段，前端删掉自造权重的三行。

**⑤ 首页呈现与档案概览不一致，且趋势是编造的**

- 信息密度不一致：同一组数字，档案概览现在是「`20 / 50 分` + 40% 进度条」，首页是「`20分` · 距目标 30分 · 较上阶段 +20分」——满分要靠「得分 + 距目标」自己加出来。
- **「较上阶段 +20分」是从缺失基线编造出来的趋势**（建议优先修，见 1.4）。

**⑥ 教师端「平均得分」与学生端不可比**

- 学生端是「一个学生的多个维度」聚合，教师端是「多个学生的同一维度」再聚合（`avgBy(rows, 'avgScore')` → KPI「平均得分」），且教师端全程不展示满分或得分率。
- 同一个字段名 `avgScore` 在两端的含义不同，且教师端的 `avgScore` 是否已按满分归一无法从接口文档确认（`GET /profile/scores` 无此字段，教师端由 `/teacher/...overview` 下发）。

### 1.4 首页「较上阶段 +20分」——建议优先修（本次未改）

- **事实**：后端 `/home/dashboard` 的 `indicators[]` 里 `comparedSemesterId: null`、`comparedSemesterName: null`、`trend: "+0"`，`radarChart.previous = [0, 0, 0]` —— 即**本期没有可比较的上期数据**。
- **前端**：`Dashboard.vue:138` `deltaFromPrevious = item.current - item.previous` = `20 - 0 = 20`；`:148` `deltaClass = delta >= 0 ? 'is-up' : 'is-down'`；`:146` 在无对比学期时把文案兜底成「较上阶段」。
- **实测渲染**（学生 202401002 登录后打开 `/dashboard`）：
  - 学业成绩 20分 · **较上阶段 +20分**（上升态绿色） · 距目标 30分
  - 竞赛实践 10分 · **较上阶段 +10分**（上升态） · 距目标 20分
  - 综合素质 0分 · 较上阶段 +0分 · 距目标 20分
- **为什么是缺陷**：把「没有上期数据」呈现成了「进步了 20 分」。并且这与项目里**已有的口径约定相互矛盾**——`src/app/stores/archive.ts:93` 明确注释「/profile/info 未返回上阶段分数，无环比数据时 previous 与 current 相同（**前端不编造趋势**）」。store 层刻意做了防护，首页这条路径却绕过了它，直接采信 `radarChart.previous = 0`。
- **建议修法**：以 `comparedSemesterId == null` 作为「无对比数据」的判据，不渲染 delta 区（或显示「暂无对比数据」），而不是拿 0 当基线。**未在本次改动**——涉及与后端确认「无上期数据」的语义，且与 1.5 的问题 3 是同一件事。

### 1.5 需要产品 / 后端确认的 5 个问题

1. 「综合评分」的正式口径是哪一种：**加权总分（0–100）** 还是 **平均得分率（%）**？李四两种情况分别是 **30 分** 与 **24%**，与现在的 **10** 都不同。
2. 权重是否以规则版本（`ruleVersion`）为准？若是，请后端在 `GET /profile/scores` 的 `list[]` 补 `weight` 字段（`/profile/scores/{id}/details` 已有同名字段，对齐即可）——这是让④的「权重」列不再是得分率的必要条件。**附带结论**：④的「加权总分」本身**不需要权重字段**即可修正——由 1.3 的推导，正确值恰为 `Σ score / Σ targetScore = 30 / 100`，即「总分 / 总满分」，现有字段已够；只有「权重」列需要后端补字段。
3. 首页雷达在 `comparedSemesterId == null` 时如何呈现：隐藏 delta / 显示「暂无对比数据」/ 其它？
4. 教师端 `avgScore` 的定义：多个学生的原始分平均，还是归一化后的得分率平均？是否应同步展示满分？
5. 简历导出文本里的「综合评分」用哪个口径（该数字会交付给第三方，影响面最大）？

# 需求六：登录入口与账号角色错配 —— 前端拒绝并提示

## 一、背景（问题复现）

学生登录页签填入教师账号 `T00003`，**登录成功**并进入学生端：页面渲染的是学生内容，右上角却是教师姓名。实测同一现象对管理员账号 `A00002` 同样成立，即**两个页签对任何账号都放行**。

根因（三处叠加）：

1. `Login.vue` 的 `handleLogin` 只按 UI 页签（`loginType`）分支，**从不校验 `res.user.roles`**，登录入口与账号角色可以不一致；
2. `toUserInfo` / `toStudentUserInfo` 把 `loginType` 写死为所选页签，账号的真实角色被丢弃；
3. 后端 `POST /auth/login` 请求体只有 `userNo / password / captcha*`，**不接收登录入口信息**，服务端无从拒绝错配。

**处理口径（用户决策）**：前端先做配套与兜底，**错配时拒绝并提示**，等待后端加固。

### 2.6 该口径的实证依据（关键，已写入 `score.ts` 与两处注释）

用 `GET /profile/scores/{id}/details` 的**指标级**权重做了数据闭合验证：

- 三个维度的指标级 `weight` 之和分别为 **0.500 / 0.300 / 0.200**，Σ = **1.000**；
- 维度得分 = `Σ(weight × rawScore)`，`rawScore` 为 0–100；
- 于是维度满分 `targetScore = Σ(该维度指标权重) × 100` = **50 / 30 / 20**，Σ = **100**，与接口返回的 `targetScore` **完全吻合**；
- 故 `Σ得分 / Σ满分 × 100` = 30，且该式同时等价于 `Σ(维度得分率 × 维度权重) × 100`，两个口径给出同一个数。

**这条闭合验证同时推翻了需求五 1.5 问题 2 中「需后端补 `weight` 字段」的前置依赖** —— 真权重可由现有字段反推。
