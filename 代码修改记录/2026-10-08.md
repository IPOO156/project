# 四、根因（已定性为隧道限流）

失败现场从 trace 中取得：**同一时刻所有 `/api/v1/*` 全部 500 且 body 为 0 字节**，连公开接口 `/api/v1/public/statistics` 也挂（说明不是某个接口的问题，是整个 API 通道中断）。

直连隧道拿到 natapp 的原话：

```
HTTP 429  "Too much connections in one mintue,Please try later"     ← natapp 原文，含拼写错误
```

即 **natapp 免费隧道的「每分钟连接数」限流**。经 Vite 代理后表现为空 body 500（本题此前已归档，见既有记录 §3.1）。

## 4.1 为什么总是挂学生端冒烟组（时序假象）

全量执行顺序为 `profile-dimension（4 用例，每次整页加载都请求多个接口）→ 学生端登录（2）→ 学生端冒烟（6）`。轮到冒烟组时累计连接数已越线；而**该组单独跑时自身突发量在限内，所以必过**。教师端排在冒烟组约 40s 的超时之后，限流窗口已滚动，因此总是通过 —— 这个「总是同一组挂」的规律极具误导性，容易读成学生端有回归。

`retries: 1` 救不回来：重试落在**同一分钟**窗口内。

## 4.2 与 10-07 记录的关系

10-07 的收尾结论（"隧道客户端掉线"）**仍然成立**，那是另一种成因（`Tunnel xxx not found`，域名已注销）。本次是新域名上线后的**限流**，两者都表现为经代理的空 body 500，只有直连读 body 才能区分：

| 直连隧道响应                                | 成因     | 处置                          |
| ------------------------------------------- | -------- | ----------------------------- |
| `429 Too much connections in one mintue...` | 限流     | 冷却，或分阶段跑              |
| `404 Tunnel xxx not found`                  | 域名注销 | 换新域名，同步两处 proxy 配置 |

### 5.1 补正：「5 did not run」不是教师端（易误读）

§四 的读数 `13 passed / 1 failed / 5 did not run` 极易被读成「学生端和教师端都挂了」，实测**不是**。算式：

| 组成                                  | 用例数        | 计入                     |
| ------------------------------------- | ------------- | ------------------------ |
| `profile-dimension`                   | 4             | passed                   |
| 学生端登录                            | 2             | passed                   |
| **教师端登录 + 教师端冒烟**           | **2 + 5 = 7** | **passed**               |
| 学生端冒烟（`student.spec.ts:36-73`） | 6             | 1 failed + 5 did not run |
| **合计**                              | **19**        | 13 / 1 / 5               |

学生冒烟组带 `test.describe.configure({ mode: 'serial' })`：`beforeAll` 登录失败时，**第一个用例**记账为 `1 failed`（指向钩子），**其余 5 个**为 `did not run` —— 与读数逐位吻合。

**即：那 4 次全量失败里，教师端 7 个用例全部是通过的**，挂的只有学生冒烟一处（限流打在它的共享登录上）。§五 括号里的「学生端 6 个、教师端 5 个」说的是**两组的规模**，不是「两组都挂了」，勿混读。
